# Design

`subsumes(a, b)` decides whether every instance valid under B is valid under A, for JSON Schema draft 2020-12. The method is *refutational normalization*, the algorithm of Baazizi, Colazzo, Ghelli, Sartiani and Scherzinger, "JSON Schema Inclusion through Refutational Normalization" ([arXiv:2603.25306](https://arxiv.org/abs/2603.25306)).

The [README](README.md) states the goals, the verdicts and what is unsupported. This document is the plan for the implementation.

**Status:** the API, the benchmark harness, the load stage and the skeleton of the engine exist. The engine models the types, `null`, the booleans, numbers, strings, objects, arrays, the connectives, `$ref`, `$dynamicRef`, `unevaluatedProperties` and `unevaluatedItems`, and answers `Unknown` where the answer depends on another keyword. The rest of the [pipeline](#pipeline) is still to be built, in the [order of work](#order-of-work) below.

## Method

A subsumes B exactly when no instance satisfies `all[B, not A]`. The engine normalizes that conjunction into a disjunction of *canonical conjunctions*, each of them satisfiable by construction or refuted to `false`.

- No conjunction is left: `Yes`.
- A conjunction is left: a counterexample is generated from it, and the verdict is `No`.
- Every conjunction left contains something the engine cannot model, or the budget ran out: `Unknown`.

## Decisions

- **Sound before complete.** What cannot be modelled exactly becomes an `Unknown` leaf. A leaf never refutes a conjunction and never contributes to a counterexample.
- **Equal leaves cancel.** Two leaves from the same keyword with the same value are one predicate, so `u ∧ ¬u` is refuted. A schema subsumes itself even if it contains `uniqueItems: true`.
- **Three causes of the verdict `Unknown`.** An unsupported construct, reported with its schema and location, the budget, or a counterexample that cannot be written. A check that needs the infinite unfolding of a recursive schema counts as the first, and names the schema in which the cycle closes. The third is an instance that tells the two schemas apart and that the library cannot give: a number when none was found that a JSON value holds exactly, or a value of more than 127 objects inside one another. It has no location, because no keyword is at fault.
- **One budget, in steps.** Everything that can blow up charges it: insertions into canonical conjunctions, DFA states, dynamic scopes and schemas that are reached in more than one, `unevaluated*` scenarios, the search for a counterexample, nesting depth. There is no other limit on the work, and nothing in the engine recurses on how deep the schemas are, so a deep schema runs out of steps and never out of stack. A value is copied and dropped one level inside the other, which is why a counterexample has a greatest depth; see [Generate](#generate). Steps do not depend on the machine, so a pair gets the same verdict everywhere. The budget is there to end a check, not to measure it: a step is a few nanoseconds of work in one place and more than a hundred in another, so the steps of a check are no goal, and speed is the time of a run over the corpus. The default is 10 million steps. On the laptop it was set on, the slowest check of the corpus that spends them all takes about two seconds, and the corpus takes about six minutes on one core. It is 20 times the first default, which decided 113 checks fewer.
- **Invalid input is an error, not a verdict.** A root that is no schema, another dialect, a keyword of the wrong shape, an `$id` or an anchor declared twice, a reference that resolves to nothing. Each error names the schema and the location. A pattern that the `regex` crate rejects is not an error but an `Unknown` leaf.
- **No validator in the library.** A counterexample is returned unchecked. Tooling outside the library checks counterexamples; see [Testing](#testing).
- **Patterns are parsed by `regex-syntax`**, so the dialect is that of the `regex` crate by construction. The DFAs are our own; see [String languages](#string-languages).
- **`format` is asserted** for the formats whose strings are a regular language that can be written down exactly: `date`, `time`, `date-time`, `duration`, `uuid`, `ipv4`, `ipv6`, `uri`, `uri-reference`, `json-pointer`, `relative-json-pointer`. One table of patterns in the Rust dialect defines them, each after the grammar of the document that defines the format. `ipv4` is the one pattern that is narrower than its grammar: RFC 2673 gives a number of an address one to three digits, so `01.2.3.4` is an address by the letter. The corpus has `087.10.0.1` as no address, as the test suite that it is made from, and validators take no number with a zero before it, which some programs read as octal. The library follows the corpus and the validators there. Any other format is an `Unknown` leaf. `hostname` and `email` are among them: they are not supported yet; see [left for later](#left-for-later).
- **A format may be modelled in part.** Then one pattern holds the strings that the format accepts, a second one those of which it is left open, and every other string the format rejects. `time` and `date-time` are so: the second 60 is one only where a leap second was, which no grammar says, so a string with the second 60 is left open. `duration` is so for another reason: the grammar that the draft names allows strings that validators do not take. The letters of a duration are ABNF, which reads them in either case, so `p1d` is a duration by the letter. The corpus has no such duration to settle it, as it has for `ipv4`, so one in small letters is left open as well. None of this is supported yet; see [left for later](#left-for-later).
- **Numbers are exact.** Every bound, every `multipleOf` and every number of a `const` or an `enum` is a rational, taken from the decimal that `serde_json` prints for the number. For a float that is the shortest decimal that gives the same float, so `0.0075` is a multiple of `0.0001`. A float from 2^53 on is the whole number that it holds instead: `9.223372036854776e18` is 2^63, which ends in 808. Between two such floats lie whole numbers that a JSON value holds as integers, and the decimal would put the float on the wrong side of some of them, where a validator has it on the right one. The two integers of a rational are of any size: no number is too large to keep, and nothing overflows. Plain `serde_json` is enough. A `Yes` holds for every number, also for one with more digits than a float keeps. A `No` needs a number that a JSON value holds exactly; see [Generate](#generate).
- **A schema stands on its own.** A reference resolves within A, within B, or to the meta-schema of the draft or of one of its vocabularies, which the library carries. Nothing is fetched and no other document can be given: a schema spread over several files is bundled first, as the specification describes. That loses nothing and keeps the API and the load stage small.
- **The library resolves references itself.** The parser visits every subschema anyway, so it indexes each `$id` and anchor as it goes, and `fluent-uri` resolves the URIs. The `referencing` crate is made for a validator: its lookup follows the dynamic scope, it wants every referenced document present, it reads fragments loosely and it recurses. It is the oracle of the tests instead.
- **A `$ref` leads where it says, also to a dynamic anchor.** The draft has `$ref` resolved when a schema is loaded, and only `$dynamicRef` looks at the dynamic scope. The validator of the harness looks at the scope for a `$ref` too when its fragment names a `$dynamicAnchor`, as the `referencing` crate under it does. The two differ only where another dynamic anchor of the name is further out on the way, which no schema of the corpus has. The library follows the draft; see [Testing](#testing).
- **A fragment may be written loosely, and is read strictly.** The fragment of a `$ref` may hold characters that a URI does not allow, such as a space, because many schemas name their definitions that way and validators accept it. It is percent-decoded once, and a JSON Pointer in it is read as RFC 6901 defines it.
- **Pure Rust, no solver.** Dependencies: `serde_json`, `fluent-uri`, `regex-syntax`, and for the rationals `num-rational` with `num-bigint`, `num-integer` and `num-traits`.

## API

```
subsumes(&a, &b) -> Result<Verdict, Error>

Checker::new().budget(steps)
    .subsumes(&a, &b) -> Result<Verdict, Error>
    .check(&a, &b)    -> Result<Check, Error>    // the verdict and the steps spent
    .inspect(&a, &b)  -> Result<Value, Error>    // the schema graph as JSON, for the viewer; not stable
```

Schemas are `serde_json::Value`. A `Checker` does not change while it checks, so one can be shared between threads.

### Python

```
subsumes(a, b, *, budget=None) -> Yes | No(counterexample)
    raises UndecidedError    UnsupportedError(side, location) | UnrepresentableError | BudgetError
    raises SchemaError       with its side and location
```

The package `subsumes` in `python/` wraps the library. It is written for Python and is no copy of the Rust API:

- **Two verdicts and an exception.** A check returns `Yes`, which is true as a condition, or `No`, which is false and carries the counterexample. A check that the library cannot decide raises, with one class of exception for each reason. So an undecided check never passes for an answer, and code that forgets about it fails loudly. No type checker makes a caller handle it, and code that checks many pairs wraps the call in `try`.
- **`UnrepresentableError` is raised although the answer is known to be no.** A `No` carries its counterexample, and `None` is one, so a `No` without one cannot be told from a `No` with `null`.
- **Two families of exceptions.** `SchemaError` is a `ValueError`: the caller's schema is at fault. `UndecidedError` is not, and the two share no base, so catching one never swallows the other.
- **A schema is a Python object,** as `json.load` gives it: `dict`, `list`, `str`, `int`, `float`, `bool` and `None`. Anything else is a `TypeError` that names where it stands, also a `tuple`. A string is the JSON string, never JSON text.
- **Numbers cross as `serde_json` would read them from text.** An `int` that 64 bits hold stays an integer, and a larger one becomes the nearest float. A `float` goes over as it is: Python and `serde_json` both print the shortest decimal that gives the float, so it stands for the same decimal on both sides. `nan`, the infinities and an `int` beyond the largest float are a `ValueError`.
- **A schema is nested 127 deep at most,** which is what `serde_json` reads from text. A deeper one is a `ValueError`. The walk over a schema recurses, and so does the drop of a `serde_json` value, and running out of stack there would crash the interpreter instead of raising.
- **`budget` is a keyword and there is no `Checker`.** With one setting, a class holds nothing. `None` is the default of the library, so the number stands in one place. `check` with its steps and `inspect` are left out: they serve the harness.
- **The GIL is released for the check,** which touches no Python object, so threads check pairs side by side.
- **The classes are Python, the native module is one function.** It returns a tuple of plain values that begins with the kind of outcome, and the package makes the dataclasses and the exceptions of it. The stub of the native module is a few lines, and ruff, ty and pytest check everything else as source.
- **One wheel for a platform,** through the stable ABI of Python 3.12, which is the oldest version supported: the first with the `type` statement.

## Pipeline

```
load       Value          ->  schema graph      typed keywords per subschema, references resolved, locations kept
lower      schema graph   ->  terms             the rewrites, the unevaluated* scenarios, variables
normalize  all[B, not A]  ->  canonical DNF
generate   conjunction    ->  counterexample
```

### Load

- A subschema is a *node*: a boolean, or a struct with one typed field per keyword that says what a schema accepts, and its children as node ids. Nodes are parsed by hand from the `Value`, not derived with serde.
- Loading has two steps. The first parses A and B from top to bottom. As it goes, it resolves each `$id` against the base URI around it, and indexes the resources by their URI and the anchors by their resource and name. The second resolves every reference to a node.
- Load parses every subschema of A and of B before the engine starts. A keyword of the wrong shape is an error wherever it stands, even in a definition that nothing uses. Input errors come from this stage only: lowering and the engine cannot fail on input.
- Every node keeps its location, a URI reference with a JSON Pointer fragment. Leaves and errors report it.
- The shape of a keyword is the one that the meta-schema of the draft gives it. That includes the keywords of older drafts which the meta-schema still describes, such as `dependencies`; they assert nothing, and an `$id` or an anchor under `dependencies` names nothing. Keywords that the draft does not define are ignored, as the specification says. Keywords that only annotate, such as `title`, are not read either.
- A count such as `minItems` is a `u64`. One that is larger, such as `1e30`, is kept as "beyond", and the engine answers `Unknown` where the answer depends on it. So is one written as a float from 2^53 on: such a float does not hold every integer, so it need not be the count that was written.
- A reference names a resource and a place in it. The resource is the one the reference stands in, one of the same schema by its URI, or a meta-schema. The place is the fragment: empty, a JSON Pointer or an anchor. A and B are resolved apart, because two versions of a schema usually share an `$id`.
- Resolution is static. A `$dynamicRef` gets the target that a `$ref` would have, and it is noted whether its fragment names the `$dynamicAnchor` of that target. Only then does it look for an anchor in the dynamic scope, which is for the lowering; otherwise it is a `$ref`, as the draft has it.
- A reference may point to a value where the draft puts no schema, such as `#/x-shared/name`. The value is parsed as a schema when the reference is resolved. No reference can name what it declares, because the draft does not look for an `$id` or an anchor there. A `$dynamicAnchor` there is bound in no dynamic scope either.
- Such a reference must not pass an `$id` on its way that stands where the draft puts no schema either. What is below that `$id` belongs to its resource if the object is read as a schema and to the resource around it if not, and a validator does one or the other depending on how it gets there. The library refuses the reference with an error, so the graph does not depend on the order of the references.
- A meta-schema is parsed when a reference leads to it, once for each of the two schemas.
- Load charges nothing to the budget. Its work grows with the size of the schemas, with one exception: every nested `$id` keeps its whole base URI, so the memory for them grows with the square of their nesting depth. A schema that was read from JSON text is at most 128 levels deep, which `serde_json` enforces.

### Lower

The engine works on *terms*, not keywords:

| Type | Terms |
| --- | --- |
| any | `True`, `False`, `TypeIs`, `AllOf`, `AnyOf`, `OneOf`, `Not`, `Ref`, `Unknown` |
| boolean | `BoolConst` |
| number | `NumConst`, `Min`, `Max`, `ExMin`, `ExMax`, `Mof` |
| string | `StrConst`, `Patt` over a regular language, `MinLen`, `MaxLen` |
| object | `PProp`, `PReq`, `PNames`, `MinProps`, `MaxProps` |
| array | `Item`, `AddIts`, `Contains`, `MinIts`, `MaxIts` |

- **Variables.** A nested subschema (a property, an item, a `contains`) is never an inline term: the term about it names its variable. What the value of a property or an item has to satisfy is a *c-reference*: a set of variables, each as it stands or negated, that denotes their conjunction. The engine makes one where several schemas meet in one property or at one position. This keeps canonical forms flat and lets results be shared.
- **Every schema that is reached has a variable:** the two roots, what a connective or a `$ref` leads to, and the schema of a property or of an item. The term of the variable is the conjunction of what its keywords say. A value inside a constant that is an array or an object has a variable too, whose term is that the instance is that value. Schemas of one [class](#data-layout) share a variable.
- **What is modelled so far** is the types, `null`, the booleans, numbers, strings, objects, arrays, the connectives, `$ref`, `$dynamicRef`, `unevaluatedProperties` and `unevaluatedItems`. Every other keyword is an `Unknown` leaf, which keeps the place where it stands, until its step of the order of work makes it a term.
- **A leaf is about the instances its keyword is about.** `uniqueItems` says something about arrays only, so a number satisfies its leaf and no number satisfies the negation.
- **A term about numbers is about numbers only,** as a leaf is about its type: a string satisfies `Min(q)`, as it satisfies `minimum`. `NumConst(q)` is like `BoolConst`: nothing but the number `q` satisfies it.
- **A term about strings is about strings only,** in the same way: a number satisfies `Patt(l)` and `MinLen(n)`, and nothing but the string `w` satisfies `StrConst(w)`.
- **A term about objects is about objects only:** a string satisfies `PProp(l, x)`, `PReq(l)` and `MinProps(n)`. `PProp(l, x)` says that every property with a name of the language `l` has a value that `x` accepts, and `PReq(l)` that some property has a name of `l`.
- **A term about arrays is about arrays only:** a string satisfies `Item(i, x)`, `Contains(x)` and `MinIts(n)`. `Item(i, x)` says that the item at position `i`, if there is one, is a value that `x` accepts, `AddIts(n, x)` that every item from position `n` on is, and `Contains(x)` that some item is.
- **What is not read as a language stays a leaf:** a pattern that the `regex` crate does not take, one that asks where a word or a line begins or ends, a format that is not modelled, and a count that was too large to keep. So does `additionalProperties` next to a pattern of `patternProperties` that is not read, since which properties it is about is not known then.
- **Two leaves are one when they must hold for the same instances:** the same keyword with the same value, or with subschemas of the same class. Keywords that depend on each other are one leaf: `contains` with its bounds, where they ask for a number of items that is not modelled. `unevaluatedProperties` and `unevaluatedItems` depend on the whole schema around them, so where one is a leaf, the leaf is one of that schema's class. A count that was too large to keep is like no other.
- **Negation moves one level at a time.** `not(Min(q))` is a number that satisfies `ExMax(q)`. The engine keeps a negation with the term that it negates, so `not(Mof(q))` and `not(NumConst(q))` are no terms of their own: the canonical conjunction keeps what they exclude. So it is with strings: `not(Patt(l))` is a string outside the language, and `not(StrConst(w))` takes one string out. And with objects: `not(PProp(l, x))` is an object with a property that has a name of `l` and a value that `x` does not accept, and `not(PReq(l))` is an object without a property of such a name. And with arrays: `not(Item(i, x))` is an array with an item at position `i` that `x` does not accept, `not(AddIts(n, x))` is one with such an item at position `n` or after it, and `not(Contains(x))` is one in which `x` accepts no item, so every item satisfies the negation of `x`. A c-reference holds a variable as it stands or negated, so the negation of a schema needs no variable of its own.
- **`$ref` and `$dynamicRef`** targets are variables. What a `$dynamicRef` leads to depends on the way that led to it: of the resources on the way from the root, the outermost one with a dynamic anchor of the name is the one whose anchor is meant. That way is a way through the schemas, and no instance has a part in it, so it is followed before there are terms. All that matters of a way is, for each name, the first resource on it that has a dynamic anchor of the name; that is the *dynamic scope*, and a name that is bound stays bound. The lowering walks from A and from B over every pair of a schema and the scope that it is reached in, and a `$dynamicRef` is a reference to the pair that it leads to. Classes and variables are of such pairs. So a schema that is reached in two scopes has two variables where it says two things, and one where it says the same in both, and the engine sees references only. Only the names that some `$dynamicRef` looks for are bound, so schemas without one have one scope, and each schema that A or B leads to is one pair. A schema that neither leads to, such as a definition that no reference names, is in no pair and has no part in the check. A scope costs a step for each name that it binds, and a pair beyond the first of a schema costs one. What entering a resource makes of a scope is worked out once for the two. A `$dynamicAnchor` says nothing of an instance, so two schemas that differ in one alone are of one class.
- **Rewrites.**
  - `prefixItems` becomes an `Item` for each position, and `items` an `AddIts` from the position after those. `contains` becomes `Contains`, also with a `minContains` of one, and nothing at all with a `minContains` of none. With a `maxContains`, or with a `minContains` of two or more, the three are one leaf; see [left for later](#left-for-later).
  - `integer` is `number` with `multipleOf: 1`.
  - `format` becomes `Patt` over the language of its pattern. A format that is modelled in part is `Patt` over what it accepts, or `Patt` over what it leaves open together with a leaf, which stands for what the format makes of those strings.
  - `const` and `enum` become the structural terms that denote exactly those values. An array is `TypeIs(array)`, an `Item` for each position and both bounds on the number of items. An object is `TypeIs(object)`, a `PProp` and a `PReq` for each name, and `MaxProps` with the number of names, which leaves no other property. Each value inside has a variable, whose term is that the instance is that value, and a value that is met again has the variable that it had. A value that is nested deeper than an instance may be, which is 127 levels, is not taken apart: it is a leaf that is like no other.
  - `if`/`then`/`else`, `dependentRequired` and `dependentSchemas` become combinations of `AnyOf`, `AllOf` and `Not`. `oneOf` stays one term, `OneOf`, because written out it takes the square of its length; the engine writes out only what it gets to.
  - `properties`, `patternProperties` and `additionalProperties` become `PProp` over a language each: the one name, what the pattern matches, and every name that is none of the names and that no pattern matches. That last language is kept as the languages that it is outside of, and no DFA is built for it. `required` becomes a `PReq` for each name.
  - `propertyNames` becomes `PNames(x)`, whose language is the string language of `x`. The engine works that language out when it gets to the term: it takes `x` apart for strings only and follows every branch to its end, and the strings that the branches leave are the language. If a branch holds a leaf about strings, no language says which strings `x` accepts, and the term is a leaf.
- **`unevaluatedProperties`** is about the properties that nothing in its schema evaluates. A schema evaluates what `properties` names, what `patternProperties` matches, and every property with an `additionalProperties` or an `unevaluatedProperties` of its own; and what the schemas *in place* evaluate that are asked of the instance and accept it: those of `allOf`, the target of `$ref` and of `$dynamicRef`, a branch of `anyOf` or `oneOf` that the instance satisfies, `if` with `then` where the condition is met and `else` where it is not, and a schema of `dependentSchemas` where the object has the property. A negated schema evaluates nothing, and neither does a schema beside the one with the keyword. So which properties are evaluated depends on the instance, and the term is one of several *ways*, or scenarios: in each, the instance satisfies some of the schemas in place, and every property with a name that those do not evaluate satisfies the schema of the keyword, which is a `PProp` over the language of the other names, as for `additionalProperties`. A way names only what the instance satisfies and nothing that it does not: with more satisfied, more is evaluated and less is asked, so the way that names everything that holds is satisfied whenever one that names less is. A way that asks more of the instance than another and evaluates no more is left out. Each schema in place costs a step each time it is looked at, and each way that joins a list is held against the ways of the list, at a step each, so schemas with many choices end at the budget. Next to nothing in place there is one way, and the term is the one of `additionalProperties`. The keyword is a leaf where the ways are not found: with a pattern in place that is not read as a language, with a schema that leads back to itself in place, and deeper in place than 64 schemas; see [left for later](#left-for-later).
- **`unevaluatedItems`** is lowered in the same way, with positions for names. A schema evaluates the items that `prefixItems` names, each item that the schema of `contains` accepts, however many `contains` asks for, and every item with an `items` or an `unevaluatedItems` of its own. So a way has a position, the longest list of first items among the schemas that it names, and the schemas of their `contains`. Every item from that position on satisfies the schema of the keyword or one of those of `contains`: an `AddIts` from the position, over a variable that stands for that disjunction, or over the variable of the schema itself where no `contains` is in play. A schema of `dependentSchemas` is asked of no array, so it evaluates no item. Next to nothing in place the term is the one of `items`.

### Normalize

- **Canonical conjunctions**, one per type:
  - `CNum`: an interval, the multiple, the excluded multiples, and the numbers that were taken out one by one.
  - `CStr`: one language, the intersection of every pattern, format and constant that was asked for and of the complement of every one that was asked against, plus length bounds.
  - `CObj`: what every property with a name of a language satisfies, the properties that there have to be, each with a name of a language and a c-reference for its value, and bounds on the property count. From these comes the *fragment map* when the branch asks whether an object is left: a partition of all names into fragments, each with the c-reference that every member satisfies.
  - `CArr`: a head of c-references, one for each of the first positions, a tail for every position after them, the items that there have to be, each at a position or after it and with a c-reference for its value, and bounds on the number of items.
- **A branch is a conjunction in the making.** `all[B, not A]` is taken apart into branches. A branch holds what the engine knows how to combine: the types and booleans an instance may still have, the numbers, the strings, the objects and the arrays it may still be, the leaves that must hold and those that must not, and the variables taken for true or for false.
- **Whether a number is left is decided exactly.** Several numbers to be a multiple of are the least number that all of them divide. A branch asks whether its `CNum` holds a number each time it has taken in what needs no split. Without a number to be a multiple of, an interval of more than one point always holds one, because the excluded ones lie apart. With one, the multiples in the interval are tried from zero outwards, a step for each and one for each excluded multiple that it is held against. Unless every multiple is excluded, one that is not is never far, so the search is short or ends at the ends of the interval. A branch without a number loses the type `number` and stands by what else it accepts: a string satisfies `minimum: 5` with `maximum: 3`.
- **Whether a string is left is decided exactly, and late.** A branch keeps the languages that were asked for and those that were asked against as they come in. One that is asked for and against leaves no string, which is seen without a DFA. The languages are put together when the branch has taken in what needs no split: the single strings first, then the patterns. The strings that are asked against are taken out all at once, as one set of words however many they are, at a step for each. That is before the branch splits. So a pattern that two schemas share costs nothing where its negation comes in without a split, and is a DFA by then where it comes in with one. A branch without a string loses the type `string` and stands by what else it accepts.
- **Whether an object is left is asked of its fragments.** The languages that a branch names cut all names into fragments: a name that some language lists is a fragment by itself, and the names that no language lists are cut by the patterns. A pattern that is one word between `^` and `$` lists that word, and every other pattern cuts. Every name of a fragment is asked the same, and a fragment says how many names it has, which may be without end. More names than a `u64` counts are taken for no end of them: the count would not be exact, and what is taken from it has to be. An object is left when each property that there has to be finds a name whose value can satisfy what every property of the fragment does and what this one is asked besides. Two of them share a name only where they have to: where a fragment has fewer names than they are, or where the object may not have as many properties. And there have to be names enough for the least number of properties, in fragments whose properties can have a value at all. Where several places are open, they are tried one after the other, a step for each.
- **Whether an array is left is asked of its positions.** An array has no gaps, so it ends before the first position whose item can have no value at all. Each item that there has to be needs a position: one at or after its own and before that end, whose value can satisfy what the position asks and what this item is asked besides. The first positions are tried first, which makes the shortest array. After the head every position asks the same, so there each such item gets a position of its own, and two share one only where the array may not have as many items. And there have to be items enough for the least number, each with a value. The engine is asked only about the positions that the array has, so the empty array costs no question however much the schemas ask of its items.
- **The two are one search.** A property that there has to be needs a name of a fragment, and an item a position. The search tries the places of each, one after the other, and goes back to the one before where none is left to try, at a step for each place. It is written once, in `canonical/search.rs`. What a place is, where a value may go, and whether what is placed makes an object or an array, is what the two say for themselves.
- **A value is an instance of its own.** Whether a value can satisfy a c-reference is the question that the check began with, asked of other schemas: `all[B, not A]` is the c-reference of B and the negation of A. So each c-reference is a *task*, which takes it apart into branches, and its answer is kept: no instance, an instance, or what stands between the engine and an instance. A branch that needs the answer for a value waits while the task runs. The tasks that wait are a stack, so a schema that is nested a thousand levels deep costs steps and no stack of the process. A leaf inside a value stands in the way of the object or the array too, and the check names it.
- **"Not this number" takes one number out.** As a number below or a number above, it would split the branch, and the negation of an `enum` of numbers would split it once for each. An `enum` of 640 numbers in no order, against the integers of the same range, then takes 3 million steps, and 1,300 this way.
- **What a term unfolds to waits its turn.** Terms are taken in the order in which they come up, so a variable meets its own negation, and a leaf its own, before either is opened.
- **A split is made one alternative at a time.** Each alternative is followed to its end before the next is made. So an instance is found without the alternatives after it, and a long `oneOf`, which has the square of its length in alternatives, is never written out.
- **Lazy negation.** `not(S)` is pushed one level and the result inserted. The plan is to try each branch of a refutable `AnyOf` in *fast mode* before it is expanded, which gives up instead of splitting, and to drop a branch that is refuted that way unexpanded. So far each alternative is followed as it comes; see [left for later](#left-for-later).
- **A branch that cannot give an instance is left alone,** once some branch has stood without one. From then on the answer is `No` or `Unknown`, and leaves are never taken back, so nothing that comes out of such a branch can change it. Without this, a schema with twenty choices between leaves would be a million branches.
- **References are decided when a branch asks.** When two c-references meet in a property, their conjunction is a c-reference of its own, which is decided when a branch first asks whether a value can satisfy it, and once. The plan was to replace a conjunction that says no more than one of the two by that one, which keeps `b_i ∧ ¬b_j` equal to `b_i` for `oneOf` branches that a discriminator already separates. That is [left for later](#left-for-later).
- **Recursion is a least fixed point.** A schema that refers to itself with nothing in between accepts what it can be shown to accept in finitely many steps, so no variable is taken for true on the strength of itself. A branch unfolds each variable once and keeps which unfolding asked for which, also where a reference meets a variable that was taken before. If what a variable asks for leads back to it by way of variables that are all taken for true, the branch is refuted. A way back that passes a variable taken for false is a schema that is negated inside itself, or the negation of a cycle. Neither is modelled: the branch depends on an `Unknown` leaf, which names the schema in which the cycle closes, since a term does not keep which keyword it came from. All of this concerns schemas that refer to themselves with nothing in between.
- **So it is through a property.** A schema may hold itself in a property, and then a task comes to ask for a c-reference that a task below it on the stack is still deciding. An instance is finite, so the c-reference accepts what it can be shown to accept without itself, and the task above takes it to accept nothing. What was found that way holds as long as the task below is at work. An instance stays one whatever happens, since more instances below make no fewer above. Any other answer is kept apart. It becomes an answer for good when the task below ends with no instance either, and is thrown away when that task ends with anything else. A list whose every element has to have a next one so accepts nothing, and one that may end accepts the lists that end. Through an item it is the same: an array whose every item has to be an array like itself with an item accepts nothing, and a tree of arrays accepts the trees that end.

### Generate

- So far an instance comes from a branch that stands and has a type that no leaf is about: `null`, a boolean, a number, a string, an array or an object that is still allowed.
- The normal form of B is computed first. Each of its conjunctions is conjoined with `not A` and searched for a counterexample before the next is touched, so a `No` usually comes long before the whole normal form exists.
- Generation is bottom-up and memoized per c-reference. A reference in progress has no counterexample, which is the same least fixed point.
- A number is the plainest of its `CNum`: the whole number nearest zero. Without a whole number it is the multiple nearest zero, and without a number to be a multiple of, the decimal with the fewest places.
- A number must be one that a JSON value holds exactly: an integer that a `u64` or an `i64` holds, or a float that is read as that number. The whole number after 2^64 is neither. In its place the multiples of a power of two are tried, beginning with the power that floats of this size are multiples of, which gives the next float, 2^64 + 4096. A branch whose number cannot be written gives no instance. If no other branch gives one, the verdict is `Unknown`, since A does not subsume B and there is nothing to show for it.
- A string is the shortest word of its `CStr` within the length bounds, and of several one of plain characters: a letter before a digit, and either before anything else. So `""` where it may be, `"a"` for a string that is not empty, and `"0000-01-01"` for a date. Each character of a word that is made up costs a step. A word that a schema holds, as that of a `const`, costs none: it is no longer than the schema.
- An object has the properties that there have to be and no other, unless more are needed for the least number of them. Those come from the names that no language lists first, since their values are asked the least. A name that a language lists is that name. Any other is the shortest name of its fragment that is not taken yet, and not the empty one where another will do: `"a"`, then `"b"`. A value is the instance that the task of its c-reference found, so `{"a": null}` is an object with one more property than `{}`. A step is charged for every value that is copied into an object.
- An instance holds at most 127 objects and arrays inside one another. `serde_json` reads no deeper text back, and copying or dropping a value recurses once for each level, so a deeper one could run out of stack however many steps there are. An object or an array that would be deeper is passed over for another. If there is no other, the verdict is `Unknown`, as for a number that cannot be written.
- An array is as short as it may be: the items that there have to be are at the first positions that will do, and every other position up to the last of them, or up to the least number of items, has a value that satisfies what the position asks. So `[]` where it may be, and `[null, ""]` for a second item that should have been a number. A step is charged for every value that is copied into an array, so an array of more items than the budget has steps is not given.

## String languages

Regular languages of strings are one module of the library, `language`. It uses no schema or engine types, and the rest of the library reaches it only through a narrow `pub(crate)` interface.

- **Interface.** A store of languages that the context of a check owns. It takes patterns, sets of words and the budget, and gives back languages by id. It offers intersection, union, complement and inclusion, emptiness and the shortest word within length bounds, whether a language holds a word, and how many words it has.
- **Search semantics.** A `pattern` matches when the regex matches anywhere in the string, so the language of a pattern is every string that contains a match. `^` and `$` are modelled as the two ends of the string. Any other look-around assertion is reported as unsupported and becomes an `Unknown` leaf: `\b`, and `^` and `$` as the ends of a line under `(?m)`. Of the 15,983 patterns of the corpus, 3 are so, and 13 more the `regex` crate does not take.
- **Representation.** A language that comes in as words is a set of words: these and no other, or every string but these. A pattern is a minimal DFA, a deterministic finite automaton, over classes of Unicode scalar values, with its states and classes numbered in one fixed way, so two DFAs are equal exactly when their languages are. It is made the usual way: the pattern becomes an NFA, a nondeterministic finite automaton, the subset construction makes a DFA of that, and Hopcroft's algorithm makes it minimal. An id says how a language came in: two equal ids are one language, and two ids that differ may be one language too.
- **A word between `^` and `$` is a set of one word,** and no DFA is built from the pattern: `^type$` matches `type` and no other string. That is read off the pattern as the `regex` crate parses it, so `^a\.b$` is the word `a.b`. A pattern that says anything else between the two ends, or lacks one of them, is a DFA like any other, and so is one that folds case, as `(?i)^a$`. Schemas that are made by programs name their properties so: of the 14,878 different patterns under `patternProperties` in the corpus, 14,217 are of this kind, and of the 1,115 under `pattern`, 104. Were each of them a DFA, a schema with a hundred such properties would have a hundred patterns to cut its names by: the run over the corpus then takes 60 s where it takes 19 s, 522 checks end at the budget where 168 do, and 120 fewer are decided.
- **What is outside a few languages is kept as those languages.** The fragments of an object are made from them, and a DFA only if something else asks.
- **Built late.** A pattern is parsed when it comes in, which says whether it is supported. Its DFA is built when something is asked that needs it. The pattern of a format is not even parsed before.
- **Lengths stay symbolic.** The states that a word of each length may end in are worked out length by length until they repeat. From there on arithmetic says which lengths are accepted, so a bound of a million costs no more than a small one.
- **What costs steps.** Each state of the NFA that a pattern becomes, each state of a DFA, with more for one that has many classes of characters, the states of the NFA that the search for a state of the DFA passes, each length that is looked at, and each character of a word that is made up. Sorting the characters into classes costs steps only where a pattern has hundreds of sets of characters.
- **Why our own DFAs.** `regex-automata` works on bytes and has no intersection or complement, and `minLength` counts characters. `regexsolver` has the set operations, but we cannot use it as the engine: it does not count its iterations anywhere, so its work cannot be charged to the budget. Its only limits are a cap on the number of states and a wall-clock timeout. It also matches whole strings, where a `pattern` is a search. It serves as an oracle in the tests.
- **Formats stay outside the module.** A format is a JSON Schema concept; the table defines each as a pattern.
- **A module, not a crate.** As a crate, its interface would be public API while it still changes most. The module can move into a crate of its own later; a published crate cannot be taken back.

## Data layout

- One context per check owns everything: the arenas of nodes, terms, variables and c-references, the store of languages, the memo tables and the budget. Nothing mutable outlives a check or is shared between checks.
- Everything is interned and addressed by a `u32` id. Equality is equality of ids, and memo keys are small.
- Schemas that say the same are of one *class*, and a class has one variable, also between A and B. `x ∧ ¬x` is then refuted by identity, without normalizing what is inside. Two versions of one schema share most of their subschemas, so most of them are never opened.
- Two schemas are of one class when they have the same keywords with the same values and their subschemas and reference targets are of one class in turn. A number is the same value as another when it is the same number, however the two are written: `1.0` says what `1` says. That holds inside an array or an object of a `const` or an `enum` too, and the properties of such an object are in no order. The schemas that are classed are those that A and B lead to, each once for every dynamic scope that it is reached in. For schemas on no cycle that is one pass from the leaves up. Schemas on cycles are told apart in rounds, each round by one step further in, until a round separates nothing; every round but the first charges the budget a step for each schema that is classed.
- Fast mode and the budget are ordinary return values. Recursion depth is counted, because a stack overflow would abort the process.

## Testing

- **Unit tests** per module.
- **The budget.** A test holds a number of steps only where it tests the budget itself: that a budget covers its limit and no more, and that a check which runs out spends all of it. Of everything else that costs steps, a test says that the work ends at a budget far below what it costs, or that it is done within one far above, or that it needs none. So the steps that a piece of work costs can change without a test failing. Not every charge has such a test; see [Left for later](#left-for-later).
- **The corpus.** CI runs every pull request over the pinned [benchmark](https://github.com/georg-wolflein/subsumes-benchmark) release and comments the comparison with `main`. It fails on a verdict against a label, on a counterexample that is none, on an error, and on a check that `main` decided and the pull request answers `Unknown`, unless the pull request has the label `allow-lost-verdicts`. Steps and times are reported, not enforced. The cases are checked one after the other, so that the time of a check is its own. `make benchmark JOBS=8` checks eight at once where only the verdicts matter and the wait does: the checks then share the machine, and their times are no more than a hint.
- **References.** The tests resolve references with the `referencing` crate as well, and the targets must be the same: for every reference of the corpus, which CI runs next to the benchmark, and for schemas made at random that are dense in what the corpus has little of, such as resources inside resources, relative references and anchors. The comparison finds the references by walking the JSON itself and lets the crate work out the base of each, so that a mistake of the parser shows and is not shared. The crate is a dependency of the tests only.
- **Languages.** Property tests on random patterns compare the DFAs with two oracles: the `regex` crate on which strings match, and `regexsolver` on intersection, complement and inclusion. Both are dependencies of the tests only.
- **Formats.** A test holds each pattern against strings that its format accepts and strings that it does not, as the `regex` crate reads the pattern. In the harness, the strings that the library gives for and against each format go to the validator, which has code of its own for each format. Run once over 300,000 strings for each format, made by changing a few characters of strings of the format, the validator and the patterns differ on none.
- **`No`.** The harness asks a validator about the counterexample of every `No` of a run: it must be valid under the schema whose instances were to be accepted and invalid under the schema that was to accept them. One that is not counts as a wrong verdict, whatever the label says and also where the corpus has none. The validator is the `jsonschema` crate, a dependency of the harness only, with `format` asserted. A schema that the validator does not take, such as one with a look-around in a pattern, leaves its counterexample unchecked, and the benchmark comment names it.
- **Patterns for the validator.** The `jsonschema` crate translates every pattern from ECMA 262 before it matches, whichever engine it uses, and has no option against that: `\d` becomes `[0-9]`, `.` stops at more line ends, and the set operations of a class become plain characters. So the harness first writes each `pattern` and each key of `patternProperties` as the `regex` crate reads it, with every class as the ranges it stands for, which leaves the translation nothing to change. It does so wherever the library reads a schema: where the draft puts one, and where a reference points with a pointer into its own resource. A pointer behind the URI of another resource is not followed; the corpus has none that leads where the draft puts no schema. A pattern that the `regex` crate does not take stays as it is written, and the validator reads it as ECMA 262 where it can: 5 of the 13 such patterns of the corpus, among them `^\cC$`. A test holds the validator against the `regex` crate on patterns that the two dialects read differently.
- **Dynamic references.** Besides the run above, a test in the harness holds the library and the validator to one reading: for schemas whose `$dynamicRef` is reached by one way and by another, by a way that was left, or names an `$anchor`, the library says that each is the same as a schema without a reference, and the validator accepts the same instances under both. One schema is there on which the two differ, a `$ref` to a dynamic anchor with another of the name further out, with what each of them says. A counterexample that turned on such a `$ref` would be counted as a wrong verdict; the corpus has none.
- **Objects.** The tests of `CObj` ask it things with an engine that is made up: one that says of a c-reference whether a value satisfies it by which variables it names. So they see where each property goes and what meets in it, without schemas.
- **Numbers.** A test asks a few things at random of a `CNum` and holds it against plain arithmetic over every quarter of a range: which numbers are in it, whether any is, which multiple is nearest zero, and that the number it gives for an instance is one of its own.
- **`Yes`** has nothing to validate. Beyond the labels of the corpus there are metamorphic tests: `a` subsumes `a`, `a` subsumes `allOf[a, x]`, and `anyOf[a, x]` subsumes `a`.
- **Every kind of instance.** For schemas with no schema inside a leaf, an instance matters to the engine only by its type, by which boolean, which number or which string it is, by its properties if it is an object, by its items if it is an array, and by which leaves about its type it satisfies. A test lists all of these for schemas made at random and asks a small evaluator, which reads the JSON and knows nothing of terms. Of the numbers it lists the quarters of a range: the schemas take their bounds and multiples from a few halves, so to them every number is like one of those quarters. Of the strings it lists those of up to three of the letters `a`, `b` and `c`: the schemas ask of a string only how it begins and ends, whether it holds a `b`, whether it holds anything but `a` and `b`, how long it is up to three characters, and whether it is one of a few short strings. The evaluator asks the `regex` crate whether a pattern matches. Of the objects it lists those of up to two of four names, with a few values that the schemas for values tell apart. That is not one of every kind, so a `Yes` is held against fewer objects than there are kinds; an object that the engine gives is evaluated as it is. Of the arrays it lists those of up to three of a few values, with an array and an object among them, which is not one of every kind either. The only leaves of the test are about arrays: `uniqueItems`, and a `contains` that counts its items. The engine must answer `Yes` exactly when every kind that B accepts, A accepts, `No` only with an instance that tells the two apart whatever the leaves say, and never `Unknown` where an instance of which no leaf is asked tells them apart. A second run makes definitions that refer to each other and to themselves, a third schemas that are mostly about objects, a fourth such schemas with each pattern a word between `^` and `$`, a fifth schemas that are mostly about arrays, with constants that are arrays and objects, and two more make definitions that hold each other in properties and in items. One makes schemas about objects with an `unevaluatedProperties` next to connectives and in their branches, and one schemas about arrays with an `unevaluatedItems`; there the evaluator collects the names or the positions that a schema evaluates from the schemas in place that accept the instance, at the moment it looks at it. One more makes documents of four resources that refer to each other, with dynamic anchors of two names and every way of writing a `$dynamicRef`; there the evaluator does what the draft says at the moment it comes to the reference, with the resources that it has entered and not left, where the library has worked out every way beforehand. Where definitions refer to themselves, the evaluator reads the definitions again and again until nothing changes, beginning with definitions that accept nothing. It keeps apart what a definition surely accepts and what it possibly accepts, because a negated reference turns the one into the other; where the two differ, nothing is asked of the engine.

## Looking at a check

`harness inspect a.json [b.json]` draws what the stages of a check make of two schemas and opens the picture in the browser. There is one picture for each stage, and a button for each in the page.

- **The schema graph:** every subschema with the keywords it asserts, the edges that apply a subschema, and where each reference leads. A, B and each meta-schema they reach get a frame.
- **The terms:** every variable with the parts of its term, and an edge to each variable that the term refers to. What A and B share stands in a frame of its own.

The pictures are made in two places:

- The library hands each stage over as a list of nodes and a list of edges, in one JSON value, through `Checker::inspect`. The harness cannot see the graph or the terms themselves, and the value promises no stability. The normal form can take the same shape when that stage exists.
- The picture is the only output: one HTML page with the graph in it, laid out by Graphviz, which the page loads from a CDN. A click on a node shows what it asserts and its edges, and a search finds nodes by location.

## Order of work

Each step goes through all four stages for the keywords it adds, and lands as its own pull request. The benchmark comment shows what the step decides, and its table of reasons for `Unknown` shows what blocks the most checks.

1. **Schema graph:** nodes, locations, errors, references. Done.
2. **Engine skeleton:** context, budget, terms, variables, lazy negation and fast mode; `type`, booleans, `null`, the connectives, `$ref` with recursion. First `Yes` and `No`. Done.
3. **Numbers.** Done.
4. **Strings:** the `language` module, then patterns, formats, lengths and a string in `const` or `enum` in the engine. Done.
5. **Objects:** the terms about properties, their names and their number, c-references, and a task for each value inside an instance. Done.
6. **Arrays:** the terms about items and their number, an array or an object in `const` and `enum`. Done, but for `uniqueItems` and a `contains` that counts; see below.
7. **`$dynamicRef`, `unevaluatedProperties`, `unevaluatedItems`,** each as a pull request of its own. Done.
8. **Speed:** measure the time of the checks on the corpus and bring it down, then set the default budget anew.

### Left for later

What a step left open, with the step that takes it up:

- **The negation of a cycle, for no step yet.** A branch that asks for the negation of a schema while it unfolds that same negation depends on a leaf. Under the least fixed point the negation holds there, so the reference could be passed over like any other that meets a variable taken before. It waits for a check that needs it.
- **A leaf below a property or an item in the test against every kind of instance, for no step yet.** The schema of a property or of an item holds no leaf there, where no schema refers to itself. The evaluator gives every array of an instance the same answer to a leaf, and the engine does not, so a leaf at two depths would let the engine see a kind that the evaluator does not list. The only leaves are `uniqueItems` and a `contains` that counts, with one schema.
- **The ways of evaluating multiply, for step 8.** Each schema in place that evaluates something and that an instance may satisfy or not doubles the ways of an `unevaluatedProperties` or an `unevaluatedItems`, and a way that joins a list is held against the whole list. Eight such choices in one schema cost 43,492 steps, and twelve more than the budget has. No schema of the corpus has more than three. The same can be said without the product: the names are cut into the sets that the same schemas evaluate, and for each set either one of those schemas is satisfied or every property of the set satisfies the schema of the keyword. That is one disjunction for each set, where the ways are one conjunction for each choice of schemas.
- **`unevaluatedProperties` and `unevaluatedItems` are not supported yet in three places, for no step yet.** Either is a leaf where a schema leads back to itself in place, and where the schemas in place are more than 64 deep. `unevaluatedProperties` is one where a schema in place has a pattern that is not read as a language. No check of the corpus is one of those.
- **A schema in place is looked at once for each way that leads to it, for step 8.** The walk that finds what an `unevaluatedProperties` or an `unevaluatedItems` evaluates follows every reference in place, so a schema that two references lead to is walked twice, with everything below it. Each look costs a step. Definitions that each refer twice to the one before are 2^n looks for n of them, and end at the budget from 22 on. The ways of a schema could be kept once they are found, which makes the walk one pass over the schemas. No check of the corpus ends at the budget for it.
- **The names of a way are copied for each schema in place, for step 8.** A schema in place adds what it evaluates to a way by making a new way of the two, which copies the names of both. So the time grows with the square of the schemas where the steps grow with their number: an `allOf` of 4,000 schemas with a property each takes 131 ms and 16,510 steps, and one of 2,000 takes 37 ms and 8,260 steps. Where neither side has a choice, the names could be added to the way in place.
- **Which disjunction to split first, for step 8.** A branch splits the disjunctions in the order in which it met them. With objects and arrays modelled, a schema of a hundred alternatives with thirty properties each is a search that the budget ends: 274 checks of the corpus, which take nine tenths of the time of a run. A larger budget is no remedy: 500,000 steps end 387 checks, and 15 million still end 232. The plan has two remedies that are not built: to try the alternatives of a disjunction before splitting on it and drop those that are refuted at once, and to replace a c-reference that says no more than a smaller one by that one.
- **A pattern of a few words as those words, for step 8.** A pattern such as `^(a|b)$` matches two words and no other string, and is a DFA that cuts the names of an object like any other pattern. It could be kept as its words instead, as a pattern of one word is: by asking its DFA how many words it has and listing them if they are few. Tried with up to 16 words, the run takes 153 million steps where it takes 157 million, and no verdict changes. What it helps is a schema with many such patterns: 16 checks of the corpus, of 4 schemas with about 20 patterns each such as `^description:(en|nl|pt)$`, take up to 310,777 steps where they took 36,339, which is still within the budget.
- **What a branch says about objects and arrays is looked at anew each time, for step 8.** A branch asks whether an object is left each time it has taken in a term about objects, and the answer is worked out from the start: the fragments are kept from one time to the next, and what each property satisfies is not. So it is with arrays. And a branch asks about both before it needs to: one that has a number to give is first asked whether it has an array.
- **A branch is copied for every alternative of a split, for step 8.** Each alternative begins as a clone of the branch that was split, and the clone is dropped when the alternative ends. Measured on the corpus after step 6, a run makes 33 million such copies. Cloning takes about 15% of the time of a run and dropping about 10%, most of it in the B-trees of the variables taken and of what is asked of the properties. To evaluate: one mutable branch for each task with an undo log, as a SAT solver keeps its trail. An alternative then records what it changes, and the engine backtracks by undoing it, which fits a search that follows each alternative to its end. It is the most invasive remedy: the numbers, strings, objects and arrays of a branch each need an undo, the search in `names` splits on its own, and the steps that a split charges for the copy would stand for nothing. Two smaller remedies come first, and may leave too little to gain: to hand the branch to the last alternative of a split instead of a clone, and to share the parts that an alternative does not change behind an `Rc` that is copied on write. None of them changes a verdict, so the harness can hold one run against another.
- **`maxContains`, and a `minContains` of two or more, are not supported yet, for no step yet.** `contains` with either is one leaf, which stands at the bound. The plan had a term `MaxContains` for them. An item that the schema accepts is then counted, so at most so many items may satisfy it and all the others have to satisfy its negation, which the search for an array does not do. In the corpus only cases of the draft's test suite have them: 50 have a `maxContains` and 72 a `minContains`, and 46 checks depend on one first.
- **`uniqueItems` is not supported yet, for no step yet.** It is a leaf, and 78 checks of the corpus depend on it first. An array of one item at most satisfies it, which the engine does not see either.
- **A schema of `propertyNames` that holds a leaf about strings is not supported yet, for no step yet.** Then `propertyNames` is a leaf itself. A format that is not modelled is the one such leaf in the corpus, in 4 schemas.
- **Two searches for one cycle, for step 8.** When a reference meets a variable that the branch has taken for true before, the engine looks for a way back twice: first by way of variables that are all taken for true, which refutes the branch, then by way of any, which makes the branch depend on a leaf. One search could answer both. It costs steps and never a verdict: for two schemas that need each other, 6 of the engine's 16 steps are such looks, and 4 would do.
- **`hostname` and `email` are not supported yet, for no step yet.** The draft has both, and neither is a pattern here. A host name with a label such as `xn--…` has to be one that Punycode produces, which no pattern says, and what an email address is, validators do not agree on. Both are leaves, and 59 checks of the corpus name one of them. A format can be modelled in part, as `time` is: a pattern for the strings that are surely of the format, and the rest left open.
- **The second 60 is not supported yet, for no step yet.** `time` and `date-time` leave open whether a string with the second 60 is one. The test suite of the draft and the validator take it for one when the time is 23:59:60 in UTC, on any day. As a pattern that is every hour and minute with its two offsets, which makes a DFA of 11,000 states. Tried, a check with a `time` took 40 ms and up to 346,000 steps, and the benchmark run 8.8 s where it takes 2.8 s. Left open, 23 checks of the corpus are `Unknown` that the pattern decided.
- **A `duration` in small letters is not supported yet, for no step yet.** The grammar that the draft names allows `p1d`, and the validator of the harness does not take it, as most do not; the corpus has no duration in small letters. So the library leaves open whether such a string is a duration, and a check that depends on one is `Unknown`. To say yes or no takes a ruling on which of the two the library follows, as the corpus gives for `ipv4`.
- **The speed of the DFAs, for step 8.** Nothing in the `language` module is tuned, and a step there takes two to four times as long as a step of the engine. The DFA of `uri-reference` takes 2 ms and 16,000 steps, each time a check needs it, and a few words are held against a pattern by way of its DFA. A DFA of a format that is built once for all checks would be no state of a check, and a word can be held against a pattern without a DFA. A branch asks whether a string is left before it splits, which makes a DFA of a pattern that an alternative of the split would have cancelled for nothing.
- **A number that can be written, for no step yet.** The search for the number of a counterexample looks at the plainest candidates only. A `CNum` may hold a number that a JSON value holds and that the search does not come by, such as a float with seventeen digits where a decimal with sixteen is in the interval too. The check then ends in `Unknown` where it could say `No`. The corpus has no such check.
- **Numbers of any precision, for no step yet.** `serde_json` has a feature that keeps every number as its text, and any crate of a build may turn it on. The library reads a number digit by digit, so `1e1000000000` would become an integer of a billion digits. An exponent that is larger still is a panic. Nothing guards against either, and no test runs with the feature. Only whether `multipleOf` is more than zero is read with the feature in mind: from the text, so that `1e-400` is no error.
- **The validator's own option for patterns, for the release that has it.** The `jsonschema` crate is getting an option that hands each pattern to the engine as it is written ([issue 1895](https://github.com/Stranger6667/jsonschema/issues/1895), [pull request 1897](https://github.com/Stranger6667/jsonschema/pull/1897)), which is merged and in no release yet. With it the harness writes no pattern anew: the `patterns` module and its two dependencies go, and the limits of the rewrite with them. Tried on the pull request, every verdict of the corpus stays, and the validator agrees with the `regex` crate on every pattern of the corpus. One thing changes: the validator refuses a schema with a pattern that the `regex` crate does not take, where today it reads the pattern as ECMA 262 if it can. That leaves 2 of the 1,912 counterexamples unchecked, both in cases that the corpus marks as having no meaning in the dialect.
- **Most charges have no test of their own, for no step yet.** The budget is charged in 45 places. With one of them taken away at a time, a test fails for 14 and none does for the other 31, among them every charge of `normalize` and of the search for an object. Some of the 31 share a loop with a charge that still ends it, as the charges for the positions of the head of an array do. A loop that is left with no charge would show only as a check that does not end.
- **The Python package is not released, for no step yet.** It builds and is tested on every change, and the release pull request raises its version with that of the crate. The release workflow builds no wheels and uploads nothing to PyPI yet: one wheel for each platform and a source distribution, with PyPI trusting the workflow as crates.io does. The README does not name the package either.
- **Exact integers beyond 64 bits from Python, for no step yet.** Python holds an integer of any size exactly, and the binding rounds one that 64 bits do not hold to a float, because a `serde_json` value has no other place for it. It follows the item on numbers of any precision above.
