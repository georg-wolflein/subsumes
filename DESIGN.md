# Design

`subsumes(a, b)` decides whether every instance valid under B is valid under A, for JSON Schema draft 2020-12. The method is *refutational normalization*, the algorithm of Baazizi, Colazzo, Ghelli, Sartiani and Scherzinger, "JSON Schema Inclusion through Refutational Normalization" ([arXiv:2603.25306](https://arxiv.org/abs/2603.25306)).

The [README](README.md) states the goals, the verdicts and what is unsupported. This document is the plan for the implementation.

**Status:** the API, the benchmark harness, the load stage and the skeleton of the engine exist. The engine models the types, `null`, the booleans, numbers, strings, objects, the connectives and `$ref`, and answers `Unknown` where the answer depends on another keyword. The rest of the [pipeline](#pipeline) is still to be built, in the [order of work](#order-of-work) below.

## Method

A subsumes B exactly when no instance satisfies `all[B, not A]`. The engine normalizes that conjunction into a disjunction of *canonical conjunctions*, each of them satisfiable by construction or refuted to `false`.

- No conjunction is left: `Yes`.
- A conjunction is left: a counterexample is generated from it, and the verdict is `No`.
- Every conjunction left contains something the engine cannot model, or the budget ran out: `Unknown`.

## Decisions

- **Sound before complete.** What cannot be modelled exactly becomes an `Unknown` leaf. A leaf never refutes a conjunction and never contributes to a counterexample.
- **Equal leaves cancel.** Two leaves from the same keyword with the same value are one predicate, so `u ∧ ¬u` is refuted. A schema subsumes itself even if it contains `uniqueItems: true`.
- **Three causes of the verdict `Unknown`.** An unsupported construct, reported with its schema and location, the budget, or a counterexample that cannot be written. A check that needs the infinite unfolding of a recursive schema counts as the first, and names the schema in which the cycle closes. The third is a number that tells the two schemas apart when none was found that a JSON value holds exactly. It has no location, because no keyword is at fault.
- **One budget, in steps.** Everything that can blow up charges it: insertions into canonical conjunctions, DFA states, `unevaluated*` scenarios, the search for a counterexample, nesting depth. There is no other limit, and nothing in the engine recurses, so a deep schema runs out of steps and never out of stack. Steps do not depend on the machine, so a pair gets the same verdict everywhere. The default of 500,000 comes from the Python version and is set anew once there are measurements.
- **Invalid input is an error, not a verdict.** A root that is no schema, another dialect, a keyword of the wrong shape, an `$id` or an anchor declared twice, a reference that resolves to nothing. Each error names the schema and the location. A pattern that the `regex` crate rejects is not an error but an `Unknown` leaf.
- **No validator in the library.** A counterexample is returned unchecked. Tooling outside the library checks counterexamples; see [Testing](#testing).
- **Patterns are parsed by `regex-syntax`**, so the dialect is that of the `regex` crate by construction. The DFAs are our own; see [String languages](#string-languages).
- **`format` is asserted** for the formats whose strings are a regular language that can be written down exactly: `date`, `time`, `date-time`, `duration`, `uuid`, `ipv4`, `ipv6`, `uri`, `uri-reference`, `json-pointer`, `relative-json-pointer`. One table of patterns in the Rust dialect defines them, each after the grammar of the document that defines the format. `ipv4` is the one pattern that is narrower than its grammar: RFC 2673 gives a number of an address one to three digits, so `01.2.3.4` is an address by the letter. The corpus has `087.10.0.1` as no address, as the test suite that it is made from, and validators take no number with a zero before it, which some programs read as octal. The library follows the corpus and the validators there. Any other format is an `Unknown` leaf. `hostname` and `email` are among them: they are not supported yet; see [left for later](#left-for-later).
- **A format may be modelled in part.** Then one pattern holds the strings that the format accepts, a second one those of which it is left open, and every other string the format rejects. `time` and `date-time` are so: the second 60 is one only where a leap second was, which no grammar says, so a string with the second 60 is left open. `duration` is so for another reason: the grammar that the draft names allows strings that validators do not take. The letters of a duration are ABNF, which reads them in either case, so `p1d` is a duration by the letter. The corpus has no such duration to settle it, as it has for `ipv4`, so one in small letters is left open as well. None of this is supported yet; see [left for later](#left-for-later).
- **Numbers are exact.** Every bound, every `multipleOf` and every number of a `const` or an `enum` is a rational, taken from the decimal that `serde_json` prints for the number. For a float that is the shortest decimal that gives the same float, so `0.0075` is a multiple of `0.0001`. The two integers of a rational are of any size: no number is too large to keep, and nothing overflows. Plain `serde_json` is enough. A `Yes` holds for every number, also for one with more digits than a float keeps. A `No` needs a number that a JSON value holds exactly; see [Generate](#generate).
- **A schema stands on its own.** A reference resolves within A, within B, or to the meta-schema of the draft or of one of its vocabularies, which the library carries. Nothing is fetched and no other document can be given: a schema spread over several files is bundled first, as the specification describes. That loses nothing and keeps the API and the load stage small.
- **The library resolves references itself.** The parser visits every subschema anyway, so it indexes each `$id` and anchor as it goes, and `fluent-uri` resolves the URIs. The `referencing` crate is made for a validator: its lookup follows the dynamic scope, it wants every referenced document present, it reads fragments loosely and it recurses. It is the oracle of the tests instead.
- **A fragment may be written loosely, and is read strictly.** The fragment of a `$ref` may hold characters that a URI does not allow, such as a space, because many schemas name their definitions that way and validators accept it. It is percent-decoded once, and a JSON Pointer in it is read as RFC 6901 defines it.
- **Pure Rust, no solver.** Dependencies: `serde_json`, `fluent-uri`, `regex-syntax`, and for the rationals `num-rational` with `num-bigint`, `num-integer` and `num-traits`.

## API

```
subsumes(&a, &b) -> Result<Verdict, Error>

Checker::new().budget(steps)
    .subsumes(&a, &b) -> Result<Verdict, Error>
    .check(&a, &b)    -> Result<Check, Error>    // the verdict and the steps spent
    .inspect(&a, &b)  -> Result<Value, Error>    // the schema graph as JSON, for the viewer; not stable
```

Schemas are `serde_json::Value`. A `Checker` does not change while it checks, so one can be shared between threads.

## Pipeline

```
load       Value          ->  schema graph      typed keywords per subschema, references resolved, locations kept
lower      schema graph   ->  terms             the rewrites, the unevaluated* scenarios, variables
normalize  all[B, not A]  ->  canonical DNF
generate   conjunction    ->  counterexample
```

### Load

- A subschema is a *node*: a boolean, or a struct with one typed field per keyword that says what a schema accepts, and its children as node ids. Nodes are parsed by hand from the `Value`, not derived with serde.
- Loading has two steps. The first parses A and B from top to bottom. As it goes, it resolves each `$id` against the base URI around it, and indexes the resources by their URI and the anchors by their resource and name. The second resolves every reference to a node.
- Load parses every subschema of A and of B before the engine starts. A keyword of the wrong shape is an error wherever it stands, even in a definition that nothing uses. Input errors come from this stage only: lowering and the engine cannot fail on input.
- Every node keeps its location, a URI reference with a JSON Pointer fragment. Leaves and errors report it.
- The shape of a keyword is the one that the meta-schema of the draft gives it. That includes the keywords of older drafts which the meta-schema still describes, such as `dependencies`; they assert nothing, and an `$id` or an anchor under `dependencies` names nothing. Keywords that the draft does not define are ignored, as the specification says. Keywords that only annotate, such as `title`, are not read either.
- A count such as `minItems` is a `u64`. One that is larger, such as `1e30`, is kept as "beyond", and the engine answers `Unknown` where the answer depends on it. So is one written as a float from 2^53 on: such a float does not hold every integer, so it need not be the count that was written.
- A reference names a resource and a place in it. The resource is the one the reference stands in, one of the same schema by its URI, or a meta-schema. The place is the fragment: empty, a JSON Pointer or an anchor. A and B are resolved apart, because two versions of a schema usually share an `$id`.
- Resolution is static. A `$dynamicRef` gets the target that a `$ref` would have; what the dynamic scope makes of it is for the engine.
- A reference may point to a value where the draft puts no schema, such as `#/x-shared/name`. The value is parsed as a schema when the reference is resolved. No reference can name what it declares, because the draft does not look for an `$id` or an anchor there.
- Such a reference must not pass an `$id` on its way that stands where the draft puts no schema either. What is below that `$id` belongs to its resource if the object is read as a schema and to the resource around it if not, and a validator does one or the other depending on how it gets there. The library refuses the reference with an error, so the graph does not depend on the order of the references.
- A meta-schema is parsed when a reference leads to it, once for each of the two schemas.
- Load charges nothing to the budget. Its work grows with the size of the schemas, with one exception: every nested `$id` keeps its whole base URI, so the memory for them grows with the square of their nesting depth. A schema that was read from JSON text is at most 128 levels deep, which `serde_json` enforces.

### Lower

The engine works on *terms*, not keywords:

| Type | Terms |
| --- | --- |
| any | `True`, `False`, `TypeIs`, `AllOf`, `AnyOf`, `OneOf`, `Not`, `Ref`, `Unknown` |
| boolean | `BoolConst` |
| number | `NumConst`, `Min`, `Max`, `ExMin`, `ExMax`, `Mof` |
| string | `StrConst`, `Patt` over a regular language, `MinLen`, `MaxLen` |
| object | `PProp`, `PReq`, `PNames`, `MinProps`, `MaxProps` |
| array | `Item`, `AddIts`, `Contains`, `MaxContains`, `MinIts`, `MaxIts` |

- **Variables.** A nested subschema (a property, an item, a `contains`) is never an inline term: the term about it names its variable. What the value of a property has to satisfy is a *c-reference*: a set of variables, each as it stands or negated, that denotes their conjunction. The engine makes one where several schemas meet in one property. This keeps canonical forms flat and lets results be shared.
- **Every schema that is reached has a variable:** the two roots, what a connective or a `$ref` leads to, and the schema of a property. The term of the variable is the conjunction of what its keywords say. Schemas of one [class](#data-layout) share a variable.
- **What is modelled so far** is the types, `null`, the booleans, numbers, strings, objects, the connectives and `$ref`. Every other keyword is an `Unknown` leaf, which keeps the place where it stands, until its step of the order of work makes it a term.
- **A leaf is about the instances its keyword is about.** `minItems` says something about arrays only, so a number satisfies its leaf and no number satisfies the negation. `const` and `enum` with an array or an object are the type of the value and a leaf about that type.
- **A term about numbers is about numbers only,** as a leaf is about its type: a string satisfies `Min(q)`, as it satisfies `minimum`. `NumConst(q)` is like `BoolConst`: nothing but the number `q` satisfies it.
- **A term about strings is about strings only,** in the same way: a number satisfies `Patt(l)` and `MinLen(n)`, and nothing but the string `w` satisfies `StrConst(w)`.
- **A term about objects is about objects only:** a string satisfies `PProp(l, x)`, `PReq(l)` and `MinProps(n)`. `PProp(l, x)` says that every property with a name of the language `l` has a value that `x` accepts, and `PReq(l)` that some property has a name of `l`.
- **What is not read as a language stays a leaf:** a pattern that the `regex` crate does not take, one that asks where a word or a line begins or ends, a format that is not modelled, and a count that was too large to keep. So does `additionalProperties` next to a pattern of `patternProperties` that is not read, since which properties it is about is not known then.
- **Two leaves are one when they must hold for the same instances:** the same keyword with the same value, or with subschemas of the same class. Keywords that depend on each other are one leaf: `items` with `prefixItems`, `contains` with its bounds. `unevaluatedProperties` and `unevaluatedItems` depend on the whole schema around them, so their leaf is one of that schema's class. A `$dynamicRef`, and a count that was too large to keep, are like no other.
- **Negation moves one level at a time.** `not(Min(q))` is a number that satisfies `ExMax(q)`. The engine keeps a negation with the term that it negates, so `not(Mof(q))` and `not(NumConst(q))` are no terms of their own: the canonical conjunction keeps what they exclude. So it is with strings: `not(Patt(l))` is a string outside the language, and `not(StrConst(w))` takes one string out. And with objects: `not(PProp(l, x))` is an object with a property that has a name of `l` and a value that `x` does not accept, and `not(PReq(l))` is an object without a property of such a name. A c-reference holds a variable as it stands or negated, so the negation of a schema needs no variable of its own.
- **`$ref` and `$dynamicRef`** targets are variables. A `$dynamicRef` variable is keyed by its target and the dynamic scope it was reached in, which models the dynamic scope without unfolding. That is step 7; until then a check does not get as far as the terms if A or B leads to a `$dynamicRef`, see [left for later](#left-for-later).
- **Rewrites.**
  - `prefixItems` and `items` become `Item` and `AddIts`; `contains`, `minContains` and `maxContains` become `Contains` and `MaxContains`.
  - `integer` is `number` with `multipleOf: 1`.
  - `format` becomes `Patt` over the language of its pattern. A format that is modelled in part is `Patt` over what it accepts, or `Patt` over what it leaves open together with a leaf, which stands for what the format makes of those strings.
  - `const` and `enum` become the structural terms that denote exactly those values. An array or an object in one is a leaf until step 6.
  - `if`/`then`/`else`, `dependentRequired` and `dependentSchemas` become combinations of `AnyOf`, `AllOf` and `Not`. `oneOf` stays one term, `OneOf`, because written out it takes the square of its length; the engine writes out only what it gets to.
  - `properties`, `patternProperties` and `additionalProperties` become `PProp` over a language each: the one name, what the pattern matches, and every name that is none of the names and that no pattern matches. That last language is kept as the languages that it is outside of, and no DFA is built for it. `required` becomes a `PReq` for each name.
  - `propertyNames` becomes `PNames(x)`, whose language is the string language of `x`. The engine works that language out when it gets to the term: it takes `x` apart for strings only and follows every branch to its end, and the strings that the branches leave are the language. If a branch holds a leaf about strings, no language says which strings `x` accepts, and the term is a leaf.
- **`unevaluatedProperties` and `unevaluatedItems`** are expanded by *scenarios*: every combination of branches of the in-place applicators (`allOf`, `anyOf`, `oneOf`, `if`/`then`/`else`, `$ref`, `dependentSchemas`) that can hold, with the names or positions it evaluates. A scenario is the conjunction of the branches it takes, the negation of those it does not, and `additionalProperties` or `items` over what it leaves unevaluated. Scenarios that evaluate the same set are merged.

### Normalize

- **Canonical conjunctions**, one per type:
  - `CNum`: an interval, the multiple, the excluded multiples, and the numbers that were taken out one by one.
  - `CStr`: one language, the intersection of every pattern, format and constant that was asked for and of the complement of every one that was asked against, plus length bounds.
  - `CObj`: what every property with a name of a language satisfies, the properties that there have to be, each with a name of a language and a c-reference for its value, and bounds on the property count. From these comes the *fragment map* when the branch asks whether an object is left: a partition of all names into fragments, each with the c-reference that every member satisfies.
  - `CArr`: a head of positional c-references, a tail, the `Contains` and `MaxContains` constraints and length bounds.
- **A branch is a conjunction in the making.** `all[B, not A]` is taken apart into branches. A branch holds what the engine knows how to combine: the types and booleans an instance may still have, the numbers, the strings and the objects it may still be, the leaves that must hold and those that must not, and the variables taken for true or for false. The canonical conjunction of arrays joins it with its step.
- **Whether a number is left is decided exactly.** Several numbers to be a multiple of are the least number that all of them divide. A branch asks whether its `CNum` holds a number each time it has taken in what needs no split. Without a number to be a multiple of, an interval of more than one point always holds one, because the excluded ones lie apart. With one, the multiples in the interval are tried from zero outwards, a step for each and one for each excluded multiple that it is held against. Unless every multiple is excluded, one that is not is never far, so the search is short or ends at the ends of the interval. A branch without a number loses the type `number` and stands by what else it accepts: a string satisfies `minimum: 5` with `maximum: 3`.
- **Whether a string is left is decided exactly, and late.** A branch keeps the languages that were asked for and those that were asked against as they come in. One that is asked for and against leaves no string, which is seen without a DFA. The languages are put together when the branch has taken in what needs no split: the single strings first, then the patterns. The strings that are asked against are taken out all at once, as one set of words however many they are, at a step for each. That is before the branch splits. So a pattern that two schemas share costs nothing where its negation comes in without a split, and is a DFA by then where it comes in with one. A branch without a string loses the type `string` and stands by what else it accepts.
- **Whether an object is left is asked of its fragments.** The languages that a branch names cut all names into fragments: a name that some language lists is a fragment by itself, and the names that no language lists are cut by the patterns. A pattern that matches a few words and nothing else counts as a list of them. Every name of a fragment is asked the same, and a fragment says how many names it has, which may be without end. An object is left when each property that there has to be finds a name whose value can satisfy what every property of the fragment does and what this one is asked besides. Two of them share a name only where they have to: where a fragment has fewer names than they are, or where the object may not have as many properties. And there have to be names enough for the least number of properties, in fragments whose properties can have a value at all. Where several places are open, they are tried one after the other, a step for each.
- **A value is an instance of its own.** Whether a value can satisfy a c-reference is the question that the check began with, asked of other schemas: `all[B, not A]` is the c-reference of B and the negation of A. So each c-reference is a *task*, which takes it apart into branches, and its answer is kept: no instance, an instance, or what stands between the engine and an instance. A branch that needs the answer for a value waits while the task runs. The tasks that wait are a stack, so a schema that is nested a thousand levels deep costs steps and no stack of the process. A leaf inside a value stands in the way of the object too, and the check names it.
- **"Not this number" takes one number out.** As a number below or a number above, it would split the branch, and the negation of an `enum` of numbers would split it once for each. An `enum` of 640 numbers in no order, against the integers of the same range, then takes 3 million steps, and 1,300 this way.
- **What a term unfolds to waits its turn.** Terms are taken in the order in which they come up, so a variable meets its own negation, and a leaf its own, before either is opened.
- **A split is made one alternative at a time.** Each alternative is followed to its end before the next is made. So an instance is found without the alternatives after it, and a long `oneOf`, which has the square of its length in alternatives, is never written out.
- **Lazy negation.** `not(S)` is pushed one level and the result inserted. The plan is to try each branch of a refutable `AnyOf` in *fast mode* before it is expanded, which gives up instead of splitting, and to drop a branch that is refuted that way unexpanded. So far each alternative is followed as it comes; see [left for later](#left-for-later).
- **A branch that cannot give an instance is left alone,** once some branch has stood without one. From then on the answer is `No` or `Unknown`, and leaves are never taken back, so nothing that comes out of such a branch can change it. Without this, a schema with twenty choices between leaves would be a million branches.
- **References are decided when a branch asks.** When two c-references meet in a property, their conjunction is a c-reference of its own, which is decided when a branch first asks whether a value can satisfy it, and once. The plan was to replace a conjunction that says no more than one of the two by that one, which keeps `b_i ∧ ¬b_j` equal to `b_i` for `oneOf` branches that a discriminator already separates. That is [left for later](#left-for-later).
- **Recursion is a least fixed point.** A schema that refers to itself with nothing in between accepts what it can be shown to accept in finitely many steps, so no variable is taken for true on the strength of itself. A branch unfolds each variable once and keeps which unfolding asked for which, also where a reference meets a variable that was taken before. If what a variable asks for leads back to it by way of variables that are all taken for true, the branch is refuted. A way back that passes a variable taken for false is a schema that is negated inside itself, or the negation of a cycle. Neither is modelled: the branch depends on an `Unknown` leaf, which names the schema in which the cycle closes, since a term does not keep which keyword it came from. All of this concerns schemas that refer to themselves with nothing in between.
- **So it is through a property.** A schema may hold itself in a property, and then a task comes to ask for a c-reference that a task below it on the stack is still deciding. An instance is finite, so the c-reference accepts what it can be shown to accept without itself, and the task above takes it to accept nothing. What was found that way holds as long as the task below is at work. An instance stays one whatever happens, since more instances below make no fewer above. Any other answer is kept apart. It becomes an answer for good when the task below ends with no instance either, and is thrown away when that task ends with anything else. A list whose every element has to have a next one so accepts nothing, and one that may end accepts the lists that end. Through an item the reference is inside a leaf for now.

### Generate

- So far an instance comes from a branch that stands and has a type that no leaf is about: `null`, a boolean, a number, a string or an object that is still allowed, or `[]`.
- The normal form of B is computed first. Each of its conjunctions is conjoined with `not A` and searched for a counterexample before the next is touched, so a `No` usually comes long before the whole normal form exists.
- Generation is bottom-up and memoized per c-reference. A reference in progress has no counterexample, which is the same least fixed point.
- A number is the plainest of its `CNum`: the whole number nearest zero. Without a whole number it is the multiple nearest zero, and without a number to be a multiple of, the decimal with the fewest places.
- A number must be one that a JSON value holds exactly: an integer that a `u64` or an `i64` holds, or a float that is printed as that number. The whole number after 2^64 is neither. In its place the multiples of ten are tried, then those of a hundred and so on, which gives 18446744073709552000. A branch whose number cannot be written gives no instance. If no other branch gives one, the verdict is `Unknown`, since A does not subsume B and there is nothing to show for it.
- A string is the shortest word of its `CStr` within the length bounds, and of several one of plain characters: a letter before a digit, and either before anything else. So `""` where it may be, `"a"` for a string that is not empty, and `"0000-01-01"` for a date. Each character of a word that is made up costs a step. A word that a schema holds, as that of a `const`, costs none: it is no longer than the schema.
- An object has the properties that there have to be and no other, unless more are needed for the least number of them. Those come from the names that no language lists first, since their values are asked the least. A name that a language lists is that name. Any other is the shortest name of its fragment that is not taken yet, and not the empty one where another will do: `"a"`, then `"b"`. A value is the instance that the task of its c-reference found, so `{"a": null}` is an object with one more property than `{}`. A step is charged for every value that is copied into an object, which bounds how deep an instance gets.
- Arrays choose which positions satisfy which `contains`.

## String languages

Regular languages of strings are one module of the library, `language`. It uses no schema or engine types, and the rest of the library reaches it only through a narrow `pub(crate)` interface.

- **Interface.** A store of languages that the context of a check owns. It takes patterns, sets of words and the budget, and gives back languages by id. It offers intersection, union, complement and inclusion, emptiness and the shortest word within length bounds, whether a language holds a word, and how many words it has.
- **Search semantics.** A `pattern` matches when the regex matches anywhere in the string, so the language of a pattern is every string that contains a match. `^` and `$` are modelled as the two ends of the string. Any other look-around assertion is reported as unsupported and becomes an `Unknown` leaf: `\b`, and `^` and `$` as the ends of a line under `(?m)`. Of the 15,983 patterns of the corpus, 3 are so, and 13 more the `regex` crate does not take.
- **Representation.** A language that comes in as words is a set of words: these and no other, or every string but these. A pattern is a minimal DFA, a deterministic finite automaton, over classes of Unicode scalar values, with its states and classes numbered in one fixed way, so two DFAs are equal exactly when their languages are. It is made the usual way: the pattern becomes an NFA, a nondeterministic finite automaton, the subset construction makes a DFA of that, and Hopcroft's algorithm makes it minimal. An id says how a language came in: two equal ids are one language, and two ids that differ may be one language too.
- **What is outside a few languages is kept as those languages.** The fragments of an object are made from them, and a DFA only if something else asks. A pattern that matches a few words and no other string is kept as those words once the fragments ask which words it has. Schemas that are made by programs name their properties so, as in `^type$`, and a hundred such patterns would otherwise be a hundred DFAs to cut the names by.
- **Built late.** A pattern is parsed when it comes in, which says whether it is supported. Its DFA is built when something is asked that needs it. The pattern of a format is not even parsed before.
- **Lengths stay symbolic.** The states that a word of each length may end in are worked out length by length until they repeat. From there on arithmetic says which lengths are accepted, so a bound of a million costs no more than a small one.
- **What costs steps.** Each state of the NFA that a pattern becomes, each state of a DFA, with more for one that has many classes of characters, the states of the NFA that the search for a state of the DFA passes, each length that is looked at, and each character of a word that is made up. Sorting the characters into classes costs steps only where a pattern has hundreds of sets of characters.
- **Why our own DFAs.** `regex-automata` works on bytes and has no intersection or complement, and `minLength` counts characters. `regexsolver` has the set operations, but we cannot use it as the engine: it does not count its iterations anywhere, so its work cannot be charged to the budget. Its only limits are a cap on the number of states and a wall-clock timeout. It also matches whole strings, where a `pattern` is a search. It serves as an oracle in the tests.
- **Formats stay outside the module.** A format is a JSON Schema concept; the table defines each as a pattern.
- **A module, not a crate.** As a crate, its interface would be public API while it still changes most. The module can move into a crate of its own later; a published crate cannot be taken back.

## Data layout

- One context per check owns everything: the arenas of nodes, terms, variables and c-references, the store of languages, the memo tables and the budget. Nothing mutable outlives a check or is shared between checks.
- Everything is interned and addressed by a `u32` id. Equality is equality of ids, and memo keys are small.
- Schemas that say the same are of one *class*, and a class has one variable, also between A and B. `x ∧ ¬x` is then refuted by identity, without normalizing what is inside. Two versions of one schema share most of their subschemas, so most of them are never opened.
- Two schemas are of one class when they have the same keywords with the same values and their subschemas and reference targets are of one class in turn. A number is the same value as another when it is the same number, however the two are written: `1.0` says what `1` says. A number inside an array or an object of a `const` or an `enum` is still compared as it is written. For schemas on no cycle that is one pass from the leaves up. Schemas on cycles are told apart in rounds, each round by one step further in, until a round separates nothing; every round but the first charges the budget a step for each node.
- Fast mode and the budget are ordinary return values. Recursion depth is counted, because a stack overflow would abort the process.

## Testing

- **Unit tests** per module.
- **The corpus.** CI runs every pull request over the pinned [benchmark](https://github.com/georg-wolflein/subsumes-benchmark) release and comments the comparison with `main`. It fails on a verdict against a label, on a counterexample that is none, on an error, and on a check that `main` decided and the pull request answers `Unknown`, unless the pull request has the label `allow-lost-verdicts`. Steps and times are reported, not enforced.
- **References.** The tests resolve references with the `referencing` crate as well, and the targets must be the same: for every reference of the corpus, which CI runs next to the benchmark, and for schemas made at random that are dense in what the corpus has little of, such as resources inside resources, relative references and anchors. The comparison finds the references by walking the JSON itself and lets the crate work out the base of each, so that a mistake of the parser shows and is not shared. The crate is a dependency of the tests only.
- **Languages.** Property tests on random patterns compare the DFAs with two oracles: the `regex` crate on which strings match, and `regexsolver` on intersection, complement and inclusion. Both are dependencies of the tests only.
- **Formats.** A test holds each pattern against strings that its format accepts and strings that it does not, as the `regex` crate reads the pattern. In the harness, the strings that the library gives for and against each format go to the validator, which has code of its own for each format. Run once over 300,000 strings for each format, made by changing a few characters of strings of the format, the validator and the patterns differ on none.
- **`No`.** The harness asks a validator about the counterexample of every `No` of a run: it must be valid under the schema whose instances were to be accepted and invalid under the schema that was to accept them. One that is not counts as a wrong verdict, whatever the label says and also where the corpus has none. The validator is the `jsonschema` crate, a dependency of the harness only, with `format` asserted. A schema that the validator does not take, such as one with a look-around in a pattern, leaves its counterexample unchecked, and the benchmark comment names it.
- **Patterns for the validator.** The `jsonschema` crate translates every pattern from ECMA 262 before it matches, whichever engine it uses, and has no option against that: `\d` becomes `[0-9]`, `.` stops at more line ends, and the set operations of a class become plain characters. So the harness first writes each `pattern` and each key of `patternProperties` as the `regex` crate reads it, with every class as the ranges it stands for, which leaves the translation nothing to change. It does so wherever the library reads a schema: where the draft puts one, and where a reference points with a pointer into its own resource. A pointer behind the URI of another resource is not followed; the corpus has none that leads where the draft puts no schema. A pattern that the `regex` crate does not take stays as it is written, and the validator reads it as ECMA 262 where it can: 5 of the 13 such patterns of the corpus, among them `^\cC$`. A test holds the validator against the `regex` crate on patterns that the two dialects read differently.
- **Objects.** The tests of `CObj` ask it things with an engine that is made up: one that says of a c-reference whether a value satisfies it by which variables it names. So they see where each property goes and what meets in it, without schemas.
- **Numbers.** A test asks a few things at random of a `CNum` and holds it against plain arithmetic over every quarter of a range: which numbers are in it, whether any is, which multiple is nearest zero, and that the number it gives for an instance is one of its own.
- **`Yes`** has nothing to validate. Beyond the labels of the corpus there are metamorphic tests: `a` subsumes `a`, `a` subsumes `allOf[a, x]`, and `anyOf[a, x]` subsumes `a`.
- **Every kind of instance.** For schemas with no schema inside a leaf, an instance matters to the engine only by its type, by which boolean, which number or which string it is, by its properties if it is an object, and by which leaves about its type it satisfies. A test lists all of these for schemas made at random and asks a small evaluator, which reads the JSON and knows nothing of terms. Of the numbers it lists the quarters of a range: the schemas take their bounds and multiples from a few halves, so to them every number is like one of those quarters. Of the strings it lists those of up to three of the letters `a`, `b` and `c`: the schemas ask of a string only how it begins and ends, whether it holds a `b`, whether it holds anything but `a` and `b`, how long it is up to three characters, and whether it is one of a few short strings. The evaluator asks the `regex` crate whether a pattern matches. Of the objects it lists those of up to two of four names, with a few values that the schemas for values tell apart. That is not one of every kind, so a `Yes` is held against fewer objects than there are kinds; an object that the engine gives is evaluated as it is. The engine must answer `Yes` exactly when every kind that B accepts, A accepts, `No` only with an instance that tells the two apart whatever the leaves say, and never `Unknown` where an instance that holds no array tells them apart. A second run makes definitions that refer to each other and to themselves, a third schemas that are mostly about objects, and a fourth definitions that hold each other in properties. There the evaluator reads the definitions again and again until nothing changes, beginning with definitions that accept nothing. It keeps apart what a definition surely accepts and what it possibly accepts, because a negated reference turns the one into the other; where the two differ, nothing is asked of the engine.

## Looking at a check

`harness inspect a.json [b.json]` draws what the stages of a check make of two schemas and opens the picture in the browser. There is one picture for each stage, and a button for each in the page.

- **The schema graph:** every subschema with the keywords it asserts, the edges that apply a subschema, and where each reference leads. A, B and each meta-schema they reach get a frame.
- **The terms:** every variable with the parts of its term, and an edge to each variable that the term refers to. What A and B share stands in a frame of its own.

The pictures are made in two places:

- The library hands each stage over as a list of nodes and a list of edges, in one JSON value, through `Checker::inspect`. The harness cannot see the graph or the terms themselves, and the value promises no stability. The normal form can take the same shape when that stage exists.
- The picture is the only output: one HTML page with the graph in it, laid out by Graphviz, which the page loads from a CDN. A click on a node shows what it asserts and its edges, and a search finds nodes by location.

## Layout

```
src/
  lib.rs, checker.rs, verdict.rs, error.rs    the API (exists)
  context.rs      the state of one check: arenas, memo tables, budget (exists)
  schema.rs       load: nodes, typed keywords, locations (exists)
  schema/         its two steps: parse, and link for the references (exists)
  term.rs         terms, variables, c-references, one-level negation (exists)
  lower.rs        schema graph to terms: classes, rewrites and scenarios (exists)
  inspect.rs      the stages of a check as pictures for the viewer (exists)
  normalize.rs    the engine (exists)
  canonical/      numbers (exists), strings (exists), objects (exists), arrays
  rational.rs     exact numbers: read from a JSON number, and written as one (exists)
  language/       string languages: DFAs over classes of characters, word sets (exists)
  formats.rs      the format table (exists)
  meta_schemas.rs the meta-schema of draft 2020-12 and those of its vocabularies (exists)
  generate.rs     counterexamples (exists)
harness/          the benchmark runner with its check of counterexamples, and the viewer (exists)
```

## Order of work

Each step goes through all four stages for the keywords it adds, and lands as its own pull request. The benchmark comment shows what the step decides, and its table of reasons for `Unknown` shows what blocks the most checks.

1. **Schema graph:** nodes, locations, errors, references. Done.
2. **Engine skeleton:** context, budget, terms, variables, lazy negation and fast mode; `type`, booleans, `null`, the connectives, `$ref` with recursion. First `Yes` and `No`. Done.
3. **Numbers.** Done.
4. **Strings:** the `language` module, then patterns, formats, lengths and a string in `const` or `enum` in the engine. Done.
5. **Objects:** the terms about properties, their names and their number, c-references, and a task for each value inside an instance. Done.
6. **Arrays.** `const` and `enum` are complete from here.
7. **`$dynamicRef`, `unevaluatedProperties`, `unevaluatedItems`.**
8. **Speed:** measure the checks on the corpus, then set the default budget.

### Left for later

What a step left open, with the step that takes it up:

- **`$dynamicRef`, for step 7.** A check ends in `Unknown` and names the `$dynamicRef` if A or B leads to one, wherever it is. What a `$dynamicRef` accepts depends on the schemas that led to it, and a term says the same wherever it stands. With one leaf for each `$dynamicRef`, a schema that is reached in two ways cancelled against its own negation, which gave a wrong `Yes`.
- **Deeply nested values of `const` and `enum`, for step 6.** The lowering writes such a value out to compare it with others, and that recurses, as does the viewer. A value that is nested many thousand levels deep overflows the stack and aborts the process. Only a value built in code can be that deep, because JSON text ends at 128 levels. When `const` and `enum` become structural terms, the lowering walks the values itself and counts the depth.
- **The negation of a cycle, for no step yet.** A branch that asks for the negation of a schema while it unfolds that same negation depends on a leaf. Under the least fixed point the negation holds there, so the reference could be passed over like any other that meets a variable taken before. It waits for a check that needs it.
- **The test against every kind of instance, for step 6.** Its schemas hold no schema inside a leaf and no constant that is an array or an object, because the engine does not look into either yet, and the schema of a property holds no leaf. The step that makes arrays terms adds them to the schemas of the test and to the evaluator.
- **An array or an object in `const` and `enum` is not supported yet, for step 6.** Either is a leaf. An object could be written as its properties now, but its values may be arrays, so the two come together. They are what 1,413 checks of the corpus depend on first.
- **Which disjunction to split first, for step 8.** A branch splits the disjunctions in the order in which it met them. With objects modelled, a schema of a hundred alternatives with thirty properties each is a search that the budget ends: 174 checks of the corpus, all of them `Unknown` before as well, and nearly half of the time of a run. The plan has two remedies that are not built: to try the alternatives of a disjunction before splitting on it and drop those that are refuted at once, and to replace a c-reference that says no more than a smaller one by that one.
- **A pattern of one word as that word, for step 8.** A pattern that is one word between `^` and `$`, such as `^type$`, matches that word and no other string. So it could come into the store as a set of one word and never be a DFA, also where it is a `pattern`. As it is, it becomes a DFA like any other pattern, and the fragments of an object then list its word. Tried, the run takes 153 million steps where it takes 169 million, and 18.6 s where it takes 20.2 s. No verdict changes, and 6 fewer checks end at the budget. `^type$` under `patternProperties` and `type` under `properties` would then be one term as well, which cancels without the engine looking.
- **What a branch says about objects is looked at anew each time, for step 8.** A branch asks whether an object is left each time it has taken in a term about objects, and the answer is worked out from the start: the fragments are kept from one time to the next, and what each property satisfies is not.
- **A schema of `propertyNames` that holds a leaf about strings is not supported yet, for no step yet.** Then `propertyNames` is a leaf itself. A format that is not modelled is the one such leaf in the corpus, in 4 schemas.
- **Two searches for one cycle, for step 8.** When a reference meets a variable that the branch has taken for true before, the engine looks for a way back twice: first by way of variables that are all taken for true, which refutes the branch, then by way of any, which makes the branch depend on a leaf. One search could answer both. It costs steps and never a verdict: for two schemas that need each other, 6 of the engine's 16 steps are such looks, and 4 would do.
- **`hostname` and `email` are not supported yet, for no step yet.** The draft has both, and neither is a pattern here. A host name with a label such as `xn--…` has to be one that Punycode produces, which no pattern says, and what an email address is, validators do not agree on. Both are leaves, and 59 checks of the corpus name one of them. A format can be modelled in part, as `time` is: a pattern for the strings that are surely of the format, and the rest left open.
- **The second 60 is not supported yet, for no step yet.** `time` and `date-time` leave open whether a string with the second 60 is one. The test suite of the draft and the validator take it for one when the time is 23:59:60 in UTC, on any day. As a pattern that is every hour and minute with its two offsets, which makes a DFA of 11,000 states. Tried, a check with a `time` took 40 ms and up to 346,000 steps, and the benchmark run 8.8 s where it takes 2.8 s. Left open, 23 checks of the corpus are `Unknown` that the pattern decided.
- **A `duration` in small letters is not supported yet, for no step yet.** The grammar that the draft names allows `p1d`, and the validator of the harness does not take it, as most do not; the corpus has no duration in small letters. So the library leaves open whether such a string is a duration, and a check that depends on one is `Unknown`. To say yes or no takes a ruling on which of the two the library follows, as the corpus gives for `ipv4`.
- **The speed of the DFAs, for step 8.** Nothing in the `language` module is tuned, and a step there takes two to four times as long as a step of the engine. The DFA of `uri-reference` takes 2 ms and 16,000 steps, each time a check needs it, and a few words are held against a pattern by way of its DFA. A DFA of a format that is built once for all checks would be no state of a check, and a word can be held against a pattern without a DFA. A branch asks whether a string is left before it splits, which makes a DFA of a pattern that an alternative of the split would have cancelled for nothing.
- **A number that can be written, for no step yet.** The search for the number of a counterexample looks at the plainest candidates only. A `CNum` may hold a number that a JSON value holds and that the search does not come by, such as a float with seventeen digits where a decimal with sixteen is in the interval too. The check then ends in `Unknown` where it could say `No`. The corpus has no such check.
- **Numbers of any precision, for no step yet.** `serde_json` has a feature that keeps every number as its text, and any crate of a build may turn it on. The library reads a number digit by digit, so `1e1000000000` would become an integer of a billion digits. An exponent that is larger still is a panic. Nothing guards against either, and no test runs with the feature. Only whether `multipleOf` is more than zero is read with the feature in mind: from the text, so that `1e-400` is no error.
- **The validator's own option for patterns, for the release that has it.** The `jsonschema` crate is getting an option that hands each pattern to the engine as it is written ([issue 1895](https://github.com/Stranger6667/jsonschema/issues/1895), [pull request 1897](https://github.com/Stranger6667/jsonschema/pull/1897)), which is merged and in no release yet. With it the harness writes no pattern anew: the `patterns` module and its two dependencies go, and the limits of the rewrite with them. Tried on the pull request, every verdict of the corpus stays, and the validator agrees with the `regex` crate on every pattern of the corpus. One thing changes: the validator refuses a schema with a pattern that the `regex` crate does not take, where today it reads the pattern as ECMA 262 if it can. That leaves 2 of the 1,912 counterexamples unchecked, both in cases that the corpus marks as having no meaning in the dialect.
